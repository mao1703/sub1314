用户希望在前端标签推荐列表（`li` 元素）中新增删除功能，并要求在点击“立即发布”按钮（`button`）时，将前端的删除操作（从推荐列表中删除）和新增操作同步到数据库。

**需求分析：**

1.  **前端交互**：
    *   在推荐列表的每一项（`li`）中，添加一个“删除”按钮。
    *   点击删除按钮后，该标签应从**前端显示**的 `availableTags` 列表中移除（即“用户在前端此次点击删除，保留删除操作”）。
    *   **注意**：用户要求点击删除时**仅保留操作**，而不是立即调用 API 删除。这意味着我们需要在本地维护一个“待删除标签列表”或直接操作 `availableTags` 状态，并在提交时统一处理。

2.  **数据同步**：
    *   点击“立即发布”按钮时：
        *   同步**新增**的标签（这部分逻辑在之前的 `handleSubmit` 中已经有了：`const mergedTags = Array.from(new Set([...tags, ...oldTags])).slice(0, 10);`）。
        *   同步**删除**的标签。如果用户在前端删除了推荐列表里的某个标签，那么在同步到后端时，这个标签不应该再出现在最终的列表中。

**逻辑调整方案：**

*   **状态管理**：
    *   目前的 `availableTags` 是从后端获取的初始状态。
    *   当用户在推荐列表中点击删除时，我应该从 `availableTags` 中移除该标签。
    *   不需要额外的“待删除列表”，因为只要 `availableTags` 变了，提交时我们用 `availableTags` 和当前文章的新 `tags` 进行合并即可。

*   **提交逻辑 (`handleSubmit`)**：
    *   之前的逻辑是：`oldTags` (从后端重新 fetch) + `currentTags` (当前文章标签) -> 合并 -> 保存。
    *   **新逻辑**：
        *   用户在前端操作了 `availableTags`（删除了某些）。
        *   提交时，应该基于**前端修改后的 `availableTags`** 和 **当前文章的 `tags`** 进行合并。
        *   **不再从后端重新 fetch `oldTags`**，而是信任前端的 `availableTags`（因为它包含了用户的删除操作）。
        *   或者，为了防止并发问题，可以 fetch 后端数据，然后**剔除**掉用户明确删除的标签。但用户说“保留删除操作”，最简单的理解是：最终提交的标签库 = (剩余的推荐标签) + (当前文章的新标签)。

**具体步骤：**

1.  **修改 `handleDeleteAvailableTag`**：
    *   实现从 `availableTags` 中移除标签的函数。
    *   绑定到 `li` 中的删除按钮上。

2.  **修改 `handleSubmit`**：
    *   **移除** `await api.get('/users/tags')` 的调用。
    *   **改为**使用当前的 `availableTags` 状态作为基准。
    *   合并逻辑：`const finalUserTags = Array.from(new Set([...tags, ...availableTags])).slice(0, 10);`
    *   调用 `api.post('/users/tags', { tags: finalUserTags })`。

3.  **UI 调整**：
    *   在推荐列表的 `li` 中添加删除按钮（类似 `x` 图标）。
    *   处理点击事件冒泡，避免触发 `handleAddTag`。
